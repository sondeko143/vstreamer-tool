# 0059. ストリーミング VC の VAD ゲートを 32ms 窓粒度 + emit 遅延補正にする

- Status: Proposed (refines [0053](0053-streaming-vc-fixed-block-crossfade.md))
- Date: 2026-07-25
- Related: [0019](0019-vc-silero-vad-gate.md), [0037](0037-transcription-vad-skip-gate.md), [0053](0053-streaming-vc-fixed-block-crossfade.md)（この ADR がゲート部分を refine する）, [0057](0057-streaming-input-envelope-rolling-ema.md)

## Context

実機で「発話の**最初の音節そのものが息っぽくなる**」という症状が出た。実録音(12s・発話 3 回)を実 config・実モデルで通して切り分けた結果:

**RVC の content encoder(HuBERT)の特徴抽出器 第1層 GroupNorm(ONNX 上は `InstanceNormalization`)が、解析窓全体の時間軸統計で正規化する。** streaming の解析窓は `[context 500ms | block 160ms]` しかなく、語頭ではその 76% が無音なので、正規化の分散が無音に支配される。結果、発声直前の微小入力(実測 RMS 0.002)が音声レベルの活性まで持ち上げられ、デコーダが気音として合成する。

同一音声・同一モデルで発声前 80ms を測ると **streaming 0.0449 / batch(`change_voice`) 0.000308 = +43dB**。裏づけ:

| 窓に占める無音 | 語頭ブロックの倍音性 | 定常ブロック |
|---|---|---|
| 0ms (無音なし) | 0.94 | 0.93 |
| 500ms (現行) | 0.37 | 0.93 |
| 1000ms | 0.17 | 0.93 |

- 用量反応がある。かつ**定常ブロックは無音量に一切反応しない** — 「語頭だけ」という症状と一致する。
- 左文脈の**中身だけ**を dither/音声に差し替えると、それと重ならない発声前区間のレベルが 31dB 下がる → 窓全体の統計に依存している。
- **look-ahead を足しても改善しない**(右文脈不足ではない)。
- f0 はバッチとほぼ一致し、語頭の無声フレームはバッチ側も無声 → f0/NSF は原因ではない。

モデル側の正規化は動かせない。問題は、この増幅を **streaming のゲートがそのまま通してしまう**ことにある。[0053](0053-streaming-vc-fixed-block-crossfade.md) のゲートはブロック粒度(160ms)で窓確率の **max** を採るので、語頭の 1 窓(実測 p=0.868)のせいでブロック全体が full gain で開き、その手前にある発声前の 4 窓(p=0.030/0.222/0.140/0.082)ごと通っていた。発話系 `[vc]`([0019](0019-vc-silero-vad-gate.md))は `speech_gate_mask` / `apply_vad_gate` で 32ms 窓ごとにマスクするので同じブレスを落とせる — この粒度差が、batch では起きず streaming でだけ聞こえる直接の理由。

さらに **emit は入力ブロックより手前から始まる**。crossfade + SOLA + HuBERT 受容野の末尾切り詰めぶん、出力は入力より遅れて出る(batch 出力との相互相関で実測 **51.8ms**)。ブロック粒度ゲートはこの遅延を補正していなかったので、判定が 52ms ずれた音声に当たっていた。

## Decision

streaming の VAD ゲートを **32ms 窓粒度のマスク + emit 遅延補正**にする(`vspeech/stream_vc/gate.py`)。

- **判定も適用も 32ms 窓ごと**。`window_gains(probs)` が窓ごとのゲインを返し、`apply()` がそれを emit のサンプル格子へ写す。ブロック粒度の max 判定(`speech_from_probs` / `update` / `ramp`)は廃止する。Silero 本体は従来どおり `vspeech/lib/vad.py` を読み取り専用で再利用し、確率は既にブロックごとに 5 窓ぶん計算しているので**追加の推論コストはゼロ**。
- **hangover は後方 dilation としてのみ効かせる**。`vad_hangover_ms` の意味は「最後に speech と判定した窓からゲートを開けたまま保つ時間」で、ブロック境界をまたいで持ち越す。**前方へは広げない** — 前方へ広げると語頭直前のブレスをそのまま開けてしまう(実録音へマスク単体をかけた実測: 前方 0ms で -26dB のところ、32ms 足すと -9dB まで後退する)。
- **emit 遅延を補正して重ねる**。`StreamingVc` が tick ごとに `emit_delay_samples`(= `context_len` の出力サンプル換算 − 読み出し開始位置)を公開し、ゲートはその分だけマスクをずらす。SOLA の lag で tick ごとに変わるので毎 emit 更新する。
- **ゲインは窓中心のあいだを線形補間する**(発話系 `apply_vad_gate` と同じ)。ブロック境界は前ブロックのマスクを左へ連結してから補間するので、段差(=クリック)は生じない。全窓 1.0 かつ直前も 1.0 なら恒等の高速路で、**既定 off / 常時 speech の出力は無ゲート時とビット単位で同一**。
- **初期状態は「閉」**。窓単位なら speech の窓がそのまま開くので、[0053](0053-streaming-vc-fixed-block-crossfade.md) が「開いた状態から始める」理由にしていた「全ブロック ramp が語頭を舐める」問題は起きない。起動直後・reset 直後の無音を漏らさない方を採る。

### 実測(実録音・実モデル・実 config)

| 区間 | batch(基準) | 修正前 | 修正後 |
|---|---|---|---|
| utt1 ブレス | 0.00040 | 0.04166 | **0.00391 (-20.5dB)** |
| utt3 ブレス | 0.00164 | 0.01745 | **0.00418 (-12.4dB)** |
| utt1 語頭 | 0.14276 | 0.21606 | 0.22021 (+0.2dB) |
| utt3 語頭 | 0.16824 | 0.21320 | 0.22477 (+0.5dB) |
| utt1 定常 | 0.15895 | 0.13160 | 0.14718 (+1.0dB) |
| 無音 | 0.00013 | 0.00000 | 0.00000 |

本物の語頭・定常は保持(むしろブロック ramp の減衰が無くなって僅かに増える)。副次的に、ブロック粒度ゲートが語間を丸ごと落としていた欠陥(実測 0.13942 → 0.08389)も同時に直る(修正後 0.14824)。

残差は batch 比 +20dB(声より 31dB 下)。マスクの立ち上がりが窓中心間 32ms かけて渡るぶん、ブレスの最後の ~13ms が ramp 帯に残る。可聴なら次の手は「開放だけ短い窓で立ち上げる非対称補間」または下記 dither。

## Alternatives rejected

- **HuBERT 解析窓へ dither(微小雑音)を足して正規化統計を安定させる** — 根本側に効く: 単体で +43dB → **+12dB**(実測)。だが全ブロックの変換入力に雑音を加算することになり、最適レベルがマイクレベル依存の調整パラメタになる。ゲート側の修正は変換出力に手を触れず同等以上(-20dB)の効果があるので、まずこちらを採る。残差が可聴なら再検討する余地は残す。
- **look-ahead(窓の右へ後続音声を足す)** — 実測で語頭の倍音性は改善しなかった(左文脈 500ms 固定で la=0/40/80/160ms のいずれも harm 0.25〜0.44)。右文脈不足ではないので、遅延を払う価値がない。
- **語頭で context を短くする** — 無音の割合を下げる方向だが、[0053](0053-streaming-vc-fixed-block-crossfade.md) の実機耳確認で context 500ms 未満は seam がガタつくと確定している。ブロックごとに context 長を変えると入力 shape が変わり、固定 shape・warmup 1 回の前提([0053](0053-streaming-vc-fixed-block-crossfade.md))も壊れる。
- **バッチ側 `speech_gate_mask` をそのまま使う(前後対称 dilation)** — `vad_speech_pad_ms` 相当を前方にも効かせると語頭直前のブレスが開く。実録音の生 streaming 出力へマスク単体をかけて測ると、前方 0ms の -26dB(0.0463 → 0.00226)に対し、前方 32ms では -9dB(0.0164)まで後退した。前方 0 が要件。
- **遅延補正だけ入れてブロック粒度は据え置き** — 同じ実測でブレスは 0.0463 → 0.0187(-8dB)にしかならない。粒度がボトルネックなので単独では足りない。
- **ブロック粒度の max 判定を mean/ratio に替える** — 発話系 `should_skip_vc` の ratio と同型にする案。ブロック内のどこが非音声かという情報を捨てている点は max と変わらず、語頭ブロック(1/5 窓が speech)は丸ごと落ちるか丸ごと開くかの二択になる。

## Consequences

語頭のブレスが可聴域から外れ、語間の欠落も直る。追加の推論コストは無い(窓確率は既に計算済み)。`vad_hangover_ms` は「ブロック単位の予算」から「窓単位の後方 dilation」へ意味が変わるが、単位(ms)と趣旨は同じなので既存設定はそのまま使える。

一方、ゲートの粒度が上がったぶん **`vad_threshold` の設定がシビアになる**: ブロック内 max で救われていた低確率の窓が個別に閉じるので、声が小さめのマイクでは発話中の窓が落ちうる(実測環境では発話中のブロックに窓確率 0.196〜0.203 が現れ、threshold 0.3 では閉じた)。実機で threshold を確認すること。

HuBERT の窓正規化による増幅(+43dB)自体は残っており、ゲートで可聴域外へ落としているだけである。ゲートを off にすると語頭のブレスはそのまま出る。
