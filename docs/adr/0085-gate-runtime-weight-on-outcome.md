# 0085. ランタイムの重さのゲートをパッケージ名の列挙から成果測定へ移す

- Status: Accepted
- Date: 2026-08-12
- 効力: 既定
- Related: refines [ADR-0084](0084-dependency-table-torch-gate.md)（依存表ガードは維持する）; [ADR-0080](0080-torch-free-rvc-runtime.md)（守りたい成果の出所）; [ADR-0066](0066-config-input-file-only.md)（pydantic-settings の重さ）, [ADR-0022](0022-hubert-onnx-runtime.md)（transformers の撤去）; spec [2026-08-12-outcome-based-runtime-gate-design.md](../superpowers/specs/2026-08-12-outcome-based-runtime-gate-design.md)

## Context

ランタイムが重い依存を抱えないことを守っているのは `tests/test_forbidden_imports.py` の `FORBIDDEN` というパッケージ名の列挙である。これは守りたいもの（起動が速く常駐が小さいこと）の**代理**であり、2 つの穴がある。

第一に、**名前を挙げていない依存は素通りする**。次に誰かが重いものを入れたとき、全ゲートが緑のまま常駐と起動が戻る。

第二に、**記録された根拠が今も成立するかを誰も確かめていない**。実測すると、壊れ方が 2 種類あった。

- `fairseq` の記録された根拠「requires-python を上げる際の障害」は**成立しない**。3.14 環境でも 0.12.2 が解決される。追加不能ではない。ただし torch 2.13.0 / torchaudio 2.11.0 を道連れにするので、torch を締め出せば結果的に入らない。
- `transformers` の記録された根拠「uv.lock に載るだけで `uv audit` に 3 件の勧告が入る」は、失効したのではなく**どのバージョンに解決するかで反転する**。3.14 のスクラッチプロジェクトに transformers 5.15.0 を入れて `uv audit` を回すと「Found no known vulnerabilities」終了コード 0 で、本リポジトリで `uv add transformers` を打つと 4.57.6 に解決して**勧告 7 件・終了コード 1** になる。今日は根拠が立つが、明日どちらへ転ぶかはゲートの外側（解決先と勧告データベース）が決める。禁止の根拠としては安定していない。

つまり名前ゲートは、誰も気づかないまま「もう成立しない理由」と「そのときの解決先しだいで反転する理由」を執行していた。どちらも、理由が docstring の散文に**現在形で**埋まっていて、**いつその根拠が切れるか**がどこにも書かれていないことから来ている。個々の名前の棚卸しは [ADR-0086](0086-forbidden-name-list-by-what-else-catches-it.md) が実測で引き受ける。

## Decision

ランタイムの重さは**成果で守る**。ランタイムの起動が実際に持ち込む**モジュール集合**と**常駐メモリ**を、子プロセスで測って検査する。GPU も実行時資産（モデル・設定）も要求しない。

**起動時間はゲートに使わない。** 計測は続けるが、合否の判定には使わない。

[ADR-0084](0084-dependency-table-torch-gate.md) の依存表ガード（`torch` / `torchaudio` / `faiss-cpu` が pyproject と uv.lock に現れない）は**維持する**。解決後の集合を検査する形は、下の却下案のとおりこのエコシステムで唯一機能する形だからである。

`vspeech/` が特定モジュールを import しないという**構造**の制約のうち、重さと無関係なもの（ONNX セッションの単一ファクトリなど）は本 ADR の対象外で、そのまま残る。

## Alternatives rejected

- **起動時間をゲートにする** — 守りたいものに最も近い指標だが、実測でノイズが予算を超える。同一コードでテストスイートの実行時間が 30.45s / 113.70s / 35.40s（N=3）と振れた。本 ADR の測定手段は 1 回の子プロセスから時間と常駐メモリを**同時に**取るので、その差がそのまま見える: 同一バッチの N=20 で `import vspeech.main` の時間が 1.01s〜3.69s（3.7 倍）に振れた一方、同じ 20 回の常駐メモリは 58.58〜59.21 MiB（ばらつき 1.1%）に収まり、モジュール集合は 20 回とも完全一致だった。しかも**時間のばらつきはマシンの負荷しだいで上限が無い**——静かなマシンで採り直した別の N=20 では 1.08s〜1.19s（1.1 倍）しか振れず、負荷の日にだけ落ちるゲートになる。常駐メモリとモジュール集合はどちらのバッチでも安定していた。暴れるゲートは無視されるようになり、無いより悪い。
- **uv の `constraint-dependencies` で解決時点に止める**（cargo-deny の `[bans]` に最も近い native 機構） — 実測すると **ban として機能しない**。`constraint-dependencies = ["torch<0"]` を置いた 3.14 プロジェクトで `uv add torch` は終了コード 1 で失敗するが、`uv add fairseq`（fairseq 0.12.2 → torch）は**失敗せず終了コード 0** を返し、torch を要求しない fairseq **0.6.2** へ後退して解決した。禁止を報告せず迂回し、頼んだものと違うものが黙って入る。直接追加しか止められない機構を ban と呼ぶことはできない。**本リポジトリでも同じ後退が再現する**ことを [ADR-0086](0086-forbidden-name-list-by-what-else-catches-it.md) が実測しており、そこではこの「強化」が既存の fairseq の守りを消す形で出ている。
- **cargo-deny 相当の外部ツールを導入する** — Python エコシステムに定着したものが無い（`pip-audit` / `safety` は脆弱性、`deptry` は未使用・欠落依存、`liccheck` はライセンス。いずれも「このパッケージを理由つきで禁止する」ではない）。自作すれば本 ADR の実装とほぼ同じ手間で、依存だけ増える。
- **名前ゲートのまま維持する** — 上記 2 つの穴が残る。特に「根拠が成立しなくなっても、あるいは根拠が反転しても執行を続ける」は実際に起きており、放置すれば次も気づかれない。
- **フルパイプラインの footprint（`poe vc-footprint`）をゲートにする** — 守りたいものそのものを測れるが、GPU・モデル資産・設定ファイル・静かな機材を要求する。通常のテスト実行では回せない。オンデマンドの計測手段として残し、ゲートにはしない。

## Consequences

名前を挙げていない重い依存が入った場合にも検査が失敗するようになる。失敗メッセージは増えたモジュールを名指しするので、名前ゲートの唯一の長所だった「原因を直接指す」性質は失われない。

**このゲートの射程は起動経路に限られる。torch はここに映らない。** 遅延 import される worker だけが触る依存（whisper の `faster_whisper`、rvc の `onnxruntime`）は構造上この測定に現れない。torch はその最たるもので、この経路は `ctranslate2` を読み込まない（transcription worker が遅延 import であるうえ、`faster_whisper` を関数本体へ deferred しているため。どちらも実測）。インストール済みの torch を掴むのはその `ctranslate2` なので、**`uv add torch` を打ってもこのゲートは全部緑のままである**。torch を守るのは引き続き [ADR-0084](0084-dependency-table-torch-gate.md) の依存表ガードであり、本 ADR はそれを置き換えない。本 ADR が足すのは直交する層——どの名前リストも覆っていない「無条件の起動経路に着地する重さ」——である。

**モジュール集合の基準は、機能追加によって正当に増える。** 更新の手順（差分を見て承認する形）が要る。これは新しい保守コストだが、その対象は「ランタイムが何を import しているか」であり、「誰かが思いついた重いものの一覧」を保守するより目的に近い。

常駐メモリの閾値は、測った値に対する余裕を持たせる必要がある。狭すぎれば暴れ、広すぎれば何も守らない。閾値の根拠は実測とともに記録する。

`pydantic_settings` の実測コストは、[ADR-0066](0066-config-input-file-only.md) が **pydantic を読み込んだ状態からの増分**として +13.7MB RSS / +176 モジュールと記録している。[ADR-0086](0086-forbidden-name-list-by-what-else-catches-it.md) が N=10 で採り直したところ、素のインタプリタからの単体 import は +18.75MiB / +240 モジュール、**実際の起動経路で固有なのは +1.51MiB / +31 モジュール**で、ADR-0066 の「32 モジュール / 約 1.6MB」を再現した。**モジュール数の検査はこの 31〜32 の増加を捉えるが、常駐メモリの閾値は 1.5MB を捉えない**（実測: 58.81 → 60.32 MiB で、予算 64.0 MiB に届かない）。2 つの指標は互いの穴を塞ぐ関係にあり、どちらか片方では足りない。

**昇格の裏づけとなった実測**（Python 3.14.5 / Windows 11 / `uv sync --all-extras`）。pristine な子プロセスで `import vspeech.main` を **N=20** 回:

| 指標 | 実測 | 予算 |
|---|---|---|
| モジュール数 | **716**（min 716 / max 716、ばらつき 0） | 732（max + 16） |
| トップレベル名 | **192**（20 回とも同一集合） | 集合そのものを照合 |
| 常駐メモリ（working set） | min **58.50** / median **58.80** / max **58.99** MiB | **64.0** MiB |

本ブランチは `vspeech/` / `cli/` / `pyproject.toml` / `uv.lock` を 1 行も変えていない（`git diff` が空）ので、**この値は変更の前後で同一**である。予算を記録した時点の採取（N=20 で 716 / 58.52 / 58.81 / 59.08 MiB）を再現しており、`tests/runtime_startup_baseline.json` に N とともに残っている。ゲートが実際に火を噴くことは、`vspeech/shared_context.py`（エントリポイント自身ではなく、それが推移的に import するモジュール）へ名前リストに載っていない `numpy` を 1 行入れて確認した——3 指標すべてが落ち（716 → 800 モジュール、58.8 → 67.02 MiB）、メッセージが `numpy` を名指しし、そのとき名前ゲートは 31 件すべて緑のままだった。
