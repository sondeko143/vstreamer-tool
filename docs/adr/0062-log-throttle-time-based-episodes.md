# 0062. ログ間引きを回数ベースから時間ベース + エピソード境界へ統一する

- Status: Accepted
- Date: 2026-07-26
- Related: [0050](0050-streaming-vc-separate-subsystem.md), [0051](0051-stream-transport-swappable-tiered.md), [0056](0056-stream-vc-consumer-jitter-buffer.md), spec `docs/superpowers/specs/2026-07-26-log-throttle-design.md`

## Context

`stream_vc` は実時間ループの集まりなので、underflow / drop / gap / GPU の transient error / UDP のプロトコルエラーはどれも「起きるときは毎ブロック・毎パケット起きる」性質を持つ。無条件にログすると警告自体がログを埋めて診断価値を失うため、各所で「初回 + N 回ごと」の間引きを入れてきた。

結果として `count == 1 or count % 50 == 0` という同一の述語が 6 定義(playback 3・runner 1・capture 1・udp 1)に複製され、定数 6 個はすべて 50、手動カウンタ変数が 10 個ある。`consumer` は `playback` から述語を 2 つ import し、`udp` は無名の汎用版 `_should_log` を private に持っている。共通化したい圧は既に漏れ出ている。

重複よりも重いのはアルゴリズム側の 3 つの実害である。

- **カウンタがプロセス寿命で累積する**ため、「初回」は一生に一度しか使えない。静穏を挟んで起きた別のインシデントは、累積件数が偶然 50 の倍数を跨ぐまで無言になる。長時間走らせる配信用途では、後半のインシデントほど先頭が欠ける。
- **出力レートがイベント率に紐づく。** 同じ 50 が `block_ms=160` なら 8 秒に 1 行、`80` なら 4 秒に 1 行、UDP のパケットレート基準ではさらに別の時定数になる。抑えたいのは時間あたりの行数なので、単位が合っていない。
- **収まった合図がない。** 障害がいつ止まり、どれだけ続いたかがログから読めない。

この 3 つは業界の定番実装がいずれも解いている問題でもある。absl の `LOG_EVERY_N_SEC` は時間で、zap の sampler は tick ごとにカウンタをリセットすることで、journald は `RateLimitIntervalSec` / `RateLimitBurst` と "Suppressed N messages" で解いている。

## Decision

`stream_vc` のログ間引きを、`vspeech/lib/log_throttle.py` の `LogThrottle` 1 クラスへ統一し、判定を**時間ベース + エピソード境界**にする。

- **API は `hit() -> int | None` の 1 メソッド。** 発生を 1 件記録し、ログを出すなら「そのエピソードでの通算件数」を、出さないなら `None` を返す。呼び出し側は `if (n := throttle.hit()) is not None:` と書く。件数カウンタを呼び出し側で持たない。
- **判定は 3 状態。** 初回、または直前の発生から `quiet_s` 超が経っていれば**新しいエピソード**として件数を 1 に戻し必ず返す(再武装)。継続中は件数を進め、前回ログから `min_interval_s` 以上経っていれば返し、でなければ `None` を返す。
- **静穏の検出は次の `hit()` の中で遅延判定する。** 成功パス側に「収まった」を知らせる呼び出しを足さない。実時間ループのホットパスへ新しい呼び出しを増やさないため。代償として、明示的な「回復しました」の 1 行は出ない — 次のエピソードの先頭行が暗黙の境界になる。
- **既定は `min_interval_s=5.0` / `quiet_s=10.0`。** ブロック長に依存しない。継続中の出力は 0.2 行/秒で、現行の N=50 が `block_ms=160` で示す 0.125 行/秒・`80` で示す 0.25 行/秒と同じオーダーに収まり、かつ設定で揺れない。
- **クロックは注入可能にする**(既定 `time.perf_counter`)。テストは偽クロックで境界を決定的に検証する。
- **ロックは持たない。** 対象の呼び出し元はすべて単一の asyncio イベントループ上で動く(UDP のプロトコルコールバックを含む)。absl の同種マクロはスレッド安全だが、ここではその必要がない。
- **置き場は `vspeech/lib/`。** `stream_vc` の中に置くと `consumer` → `playback` のような横参照が再発する。`vspeech/lib/telemetry.py` などと同じ、サブシステム横断の道具として置く。
- **ログ文言と telemetry は変えない。** 対象の全サイトは既に `(total %d)` を持っており、`hit()` の戻り値をそのまま渡せる。telemetry は間引きに関係なく毎回記録する(現状どおり)。

warn-once 系(VAD ゲートの fail-open、OBS のスタイル警告、transcription の警告集合)は「先頭 N 回だけ出して以後は永久に黙る」という別のアルゴリズム(absl でいう `LOG_FIRST_N`)なので、統合しない。

## Alternatives rejected

- **述語の抽出だけして回数ベースを維持する** — 定数 6・述語 6 が 1 組になり約 45 行減るが、上の 3 つの実害はすべて残る。重複は症状であって原因ではない。
- **カウンタ込みのオブジェクトにするが回数ベースのまま** — 呼び出し側のカウンタ 10 個も消えて記述は目的の形になるが、やはり「初回が一生に一度」と「ブロック長依存」は残る。同じ場所を二度触ることになる。
- **指数バックオフ(absl `LOG_EVERY_POW_2`、1/2/4/8/16…)** — 閾値を決めなくてよいのが魅力で、短時間の障害には良く効く。だが長時間続く障害ではほぼ無言になり(1000 件目以降は倍々でしか出ない)、「今もまだ壊れている」を配信中に知りたいという用途に合わない。累積カウンタである以上、再武装の問題も解けない。
- **`logging.Filter` をハンドラへ付けてグローバルに抑制する** — 呼び出し側を一切変えずに済み、キーを `(pathname, lineno)` にすれば自動で条件別になる。却下の理由は 3 つ。(a) 間引きされていることが呼び出し箇所から見えない。(b) `vspeech` 全体に効くので、一度きりの起動エラーや fail-loud の理由まで巻き込むリスクがある。(c) 「そのインシデントでの通算件数」をメッセージに載せられない — フィルタは落とすか通すかしか決められず、落とした件数を次のレコードの引数へ注入する手段がない。
- **zap 型(tick 固定 + メッセージキー別サンプリング)** — tick ごとのリセットは再武装問題を解く。だが固定 tick はエピソードの区切りと無関係に切れるので、tick 境界を跨いだだけの同一障害が「新規」として先頭行を出し直す。またメッセージ文字列をキーにする仕組みは、呼び出しサイトが 10 箇所しかないこの規模には過剰。
- **明示的な回復行(`settled()` を成功パスで呼ぶ)** — 「収まった。N 件・D 秒続いた」を出せるのは診断上いちばん親切だが、10 箇所すべての成功パスに呼び出しを足す必要があり、実時間ループのホットパスが増える。エピソード先頭行が境界を示すので、まずは無しで進める。必要になったら追加できる(`hit()` の意味は変わらない)。

## Consequences

判定が 1 箇所になり、呼び出し側は条件ごとに `LogThrottle` を 1 つ持つだけになる。約 60 行の重複定義と 10 個のカウンタ変数が消え、`consumer` → `playback` の横参照も消える。警告の出力レートが `block_ms` や transport の種類に依存しなくなる。

- **同一障害でも `quiet_s` を跨げば先頭行が出直す。** 数十秒おきに散発する障害では、現行より行数が増える場合がある(現行は累積カウンタなので出ない)。これは意図した交換で、散発する障害こそ毎回見たい。
- **明示的な「回復」ログは出ない。** 障害が止まったことは、次のエピソードの先頭行か telemetry の集計から読む。
- 閾値は 2 つに増えた(`min_interval_s` と `quiet_s`)。両方ともモジュール定数で、設定ファイルには出さない。必要になったときに露出を検討する。
- `LogThrottle` は状態を持つので、リセットのライフサイクル(ワーカー再起動・デバイス再 open)に暗黙に紐づく。インスタンスをループのローカルに持てば再 open で自然に作り直される場所と、プロトコルオブジェクトに持たせて接続の寿命に従う場所が混在する。どちらも「その条件が続いている単位」と一致していればよい。
- warn-once 系は統合しないので、`stream_vc` には引き続き 2 つの間引き idiom が併存する。
