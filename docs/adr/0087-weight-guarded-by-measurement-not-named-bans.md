# 0087. 依存の重さは名指しの禁止ではなく計測だけで守る（0084 と 0086 を supersede）

- Status: Proposed
- Date: 2026-08-12
- 効力: 既定
- Related: supersedes [ADR-0084](0084-dependency-table-torch-gate.md), [ADR-0086](0086-forbidden-name-list-by-what-else-catches-it.md); extends [ADR-0085](0085-gate-runtime-weight-on-outcome.md); [ADR-0080](0080-torch-free-rvc-runtime.md)（削減の出所）; refines [ADR-0055](0055-stream-vc-producer-consumer-role-split.md), [ADR-0078](0078-torch-free-device-resolution.md)（主張の形だけを変える）

## Context

[ADR-0080](0080-torch-free-rvc-runtime.md) が torch を外した目的は、起動時間と常駐メモリの削減だった。ところがそこから「**torch を二度と入れない**」という目的が外挿され、[ADR-0084](0084-dependency-table-torch-gate.md)（依存表に torch/torchaudio/faiss-cpu が現れないことをテストで守る）と [ADR-0086](0086-forbidden-name-list-by-what-else-catches-it.md)（名前リストを「他のゲートが捉えないもの」に絞る）が決められた。

**その目的は、このプロジェクトが実際に求めているものではない。** 止めたいのは**意図しない性能回帰**であって、特定パッケージの排除ではない。

名指しの禁止リストには**所属の原理が無い**。`faiss-cpu` は「そのとき使っていない依存が `pyproject.toml` に残っていた」というだけで入っていた。この規則に従うなら、設計判断で使わなくなった依存をすべて列挙し続けることになる。線が引けないリストは膨らみ、そして腐る — 実測でそれも確認された。`transformers` の記録された根拠（`uv audit` の勧告）は**解決先のバージョンで反転**し、`fairseq` の記録された根拠（追加不能）は**偽**だった。どちらも誰にも気づかれないまま執行が続いていた。

[ADR-0085](0085-gate-runtime-weight-on-outcome.md) の成果ゲートは、目的そのもの（起動が持ち込むモジュール集合と常駐メモリ）を測る。名前を列挙しないので、所属規則の問題が構造的に存在しない。

ただし現状の成果ゲートは**測る経路が足りない**。測っているのは `vspeech.main` の import だけで、ワーカーは遅延 import されるため、`ctranslate2` 経由で入る torch は捕まらない。エントリポイントは軽いまま、動いているパイプラインだけが重くなる — 止めたい回帰そのものが素通りする。

## Decision

依存の重さに対する保護は、**[ADR-0085](0085-gate-runtime-weight-on-outcome.md) の成果測定だけ**とする。パッケージ名を列挙して禁止するテストは置かない。

- [ADR-0084](0084-dependency-table-torch-gate.md) と [ADR-0086](0086-forbidden-name-list-by-what-else-catches-it.md) を supersede し、その実装（`FORBIDDEN` / `FORBIDDEN_DISTRIBUTIONS` と付随テスト）を削除する。**torch が依存表に戻ることを止めるものは無くなる。これは意図した結果である。**
- 「特定経路が torch を読み込まないこと」を主張していた既存テスト（[ADR-0055](0055-stream-vc-producer-consumer-role-split.md) の consumer 経路、[ADR-0078](0078-torch-free-device-resolution.md) のデバイス層）も、名指しをやめて同じ成果測定に置き換える。**0055 / 0078 の不変条件は変えない** — 変えるのは主張の形だけで、「torch が無いこと」から「その経路の重さが基準内であること」になる。
- 成果ゲートが測る**経路を広げる**。エントリポイントに加えて、実際に重くなる経路（ワーカーが遅延 import する先を含む）を測る。**名指しするのは「測る対象の経路」であって、禁止するパッケージではない。**
- タスクランナーの構成や型チェッカの在籍を固定するテストは置かない。性能回帰の検出から逸脱する。

## Alternatives rejected

- **依存表ガードだけは残す（torch だけ名指しで守る）** — 「torch の復活を止める」が目的ではない以上、残す根拠が無い。残せば、次に重いものが来たときまた名前を足すことになり、所属規則の無いリストがそのまま復活する。torch が重いことは測れば分かる。
- **名前リストに所属規則を定義して残す**（例: 常駐 X MB 以上のものだけを載せる） — 規則を書けたとしても、あるパッケージがそれを満たすかは結局測らないと分からない。測るなら成果ゲートで足りており、リストは中間生成物にすぎない。
- **成果ゲートごと廃止して何も置かない** — 性能回帰を検出する手段が消える。[ADR-0085](0085-gate-runtime-weight-on-outcome.md) の実測（`numpy` を起動経路に混入させると 716→800 モジュール / +8.2MiB で、増えたモジュールを名指しして落ちる）が、この形が機能することを示している。
- **`ty check` を backstop として固定する** — ガード付き import（`try: import torch / except ImportError`）を捕まえるのは実測上 `ty` だけだが、それを固定するのはタスクランナーの構成を拘束することであり、性能回帰の検出とは別の話。そもそも名指しの禁止を廃止すれば、捕まえるべき対象が無くなる。

## Consequences

`torch` を `uv add` しても、どのテストも止めない。**重さとして現れたときに、それを測っているゲートが捕まえる。** 捕まえられるかどうかは「どの経路を測っているか」に完全に依存するので、経路の網羅がこの決定の生命線になる。測っていない経路で重くなったものは検出されない。

保護の対象が「名前」から「経路」に移ったので、**新しいワーカーや新しい起動経路を足したときは、それを測定対象に加える**必要がある。これは名前リストの保守と違い、追加すべきかどうかが機械的に決まる（実行される経路かどうか）。

[ADR-0084](0084-dependency-table-torch-gate.md) が塞いだ穴（`uv add torch` が全ゲートを緑のまま通る）は、経路を広げることで塞ぐ。エントリポイントだけを測っている間は開いたままである。

`uv audit` は引き続き `poe check` にあり、脆弱性を持つ依存が入れば赤くなる。`transformers` の禁止が担っていた監査面積の抑制は、もともと audit が直接測っているものであって、名前リストが代理する必要はなかった。
