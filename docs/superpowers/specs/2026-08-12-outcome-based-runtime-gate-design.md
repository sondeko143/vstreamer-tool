# ランタイムの軽さを名前ではなく成果で守る

## 問題

ランタイムが重い依存を抱え込まないことを守っていたのは、パッケージ名の列挙だった。これは守りたいもの（起動が速く常駐が小さいこと）の代理でしかなく、**誰も名前を思いつかなかった依存は素通りする**。

名前の列挙には**所属の原理が無い**。あるエントリは「そのとき使っていない依存がたまたま依存表に残っていた」というだけで載っていた。この規則に従うなら、設計判断で使わなくなった依存をすべて永久に列挙し続けることになる。線が引けないリストは膨らみ、そして腐る — 実測でも確認された。あるエントリの記録された根拠は解決先のバージョンで反転し、別のエントリの記録された根拠は偽だった。どちらも誰にも気づかれないまま執行が続いていた。

止めたいのは特定パッケージの存在ではなく、**意図しない性能回帰**である。

一方、成果を測る側にも穴がある。測っているのがプロセスのエントリポイントだけだと、ワーカーは遅延 import されるため、実際に重くなる経路が測定に現れない。エントリポイントは軽いまま、動いているパイプラインだけが重くなる — 止めたい回帰そのものが素通りする。

## ゴール

- ランタイムの重さを、パッケージ名ではなく**観測可能な成果**で守る。
- 実際に実行される重い経路が測定対象に入っている。
- 名前を挙げて特定パッケージを禁止するテストを残さない。

## 非ゴール

- 起動時間をゲートにすること。実測でノイズが予算を超える（同一コードでテストスイートが 30.45s / 113.70s / 35.40s）。
- GPU や実行時資産（モデル・設定ファイル）を必要とする測定を通常のテスト実行に含めること。それらは要求に応じて実行する別の計測に任せる。
- 特定パッケージの再導入そのものを阻止すること。重さとして現れたときに捕まえるのであって、存在を禁じるのではない。
- タスクランナーの構成や型チェッカの在籍を固定すること。性能回帰の検出から逸脱する。
- 重さと無関係な構造の制約（実行プロバイダの単一ファクトリなど）の変更。
- 新しい外部ツールの導入。

## 受入基準

- [ ] 通常のテスト実行で、ランタイムが読み込むモジュール集合と常駐メモリが検査される。GPU も実行時資産も必要としない。
- [ ] 検査の対象には、ワーカーが遅延 import の先で読み込む重い依存を通る経路が含まれる。
- [ ] その検査は、名前を列挙していない新しい重い依存が入った場合にも失敗する。
- [ ] 検査が失敗したとき、メッセージは増えたモジュールを名指しし、どの経路で増えたのかを示す。
- [ ] 測定対象の経路が、本来通るはずの重い依存を通らなくなった場合にも失敗する。
- [ ] パッケージ名を挙げてその導入・import を禁止するテストが存在しない。
- [ ] 各予算に、その根拠（実測値と測定回数 N）が併記されている。
- [ ] 起動時間はゲートに使われていない。
- [ ] 通常のテスト実行を連続して繰り返しても、検査の結果が揺れない。
