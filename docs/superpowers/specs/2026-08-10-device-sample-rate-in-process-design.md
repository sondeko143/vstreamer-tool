# デバイス境界のサンプルレート変換をプロセス内で行う

## 問題

オーディオデバイスを開くとき、要求したレートがデバイスのネイティブレートと違えば、変換は PortAudio より下の OS 側で暗黙に行われる。本プロジェクトは 4 箇所すべてでそうなっている。

- ストリーミング VC の入口はマイクを 16kHz 固定で開く。
- ストリーミング VC の出口は RVC モデルのレート(40kHz 等)で開く。
- 発話系の録音は `recording.rate`(既定 16kHz)で開く。
- 発話系の再生は再生する音声ソースのレートで開く。

この OS 任せの変換には次の問題がある。

- 変換の素性(アンチエイリアス特性・遅延)がホスト API とドライバに依存し、こちらから決められない。自動テストでも検証できず、ログにも残らない。
- WASAPI 共有モードはミックスフォーマット以外のレートを拒否する(実測)。ネイティブレート以外で開く現状の実装では WASAPI をそもそも選べず、MME/DirectSound に固定されている。
- 発話系の再生は、音声ソースのレートが変わるたびにデバイスを閉じて開き直している。TTS と VC を交互に鳴らすと毎回リオープンが起きる。
- PortAudio は MME/DirectSound のデバイスに対し `default_samplerate` を 44100 固定で返す(実測: 48kHz で動作中のエンドポイントも 44100 と答える)。デバイスの報告値をそのまま信じても真のレートは分からない。

## ゴール

- 入口・出口のサンプルレート変換をプロセス内で行い、変換の品質と遅延をこちらで決められる状態にする。
- デバイスは既定でネイティブレートで開き、OS の変換段を通らない。
- 変換特性(阻止域・通過帯・ブロック境界の連続性・群遅延)が自動テストで検証される。
- 実際に開いたレートと、その決定根拠が観測できる。
- 変換によって生じる追加遅延が、ストリーミング経路のブロック長に量子化されない。
- ストリーミング VC と発話系の両方に適用される。
- 依存パッケージを増やさない。

## 非ゴール

- whisper 入力のリサンプル(ADR-0036)と RVC 内部のリサンプルの実装変更。どちらも現状維持。
- チャンネル数変換。実測でチャンネル数はデバイスを開く障害になっていない。
- 低レイテンシホスト API(WASAPI / 排他モード / WDM-KS)への既定の切り替え。選べるようにはなるが、既定のホスト API 選択は変えない。
- 入力デバイスと出力デバイスの間のクロックドリフト補償。
- 音声認識・翻訳・字幕・TTS の各ワーカーの挙動変更。
- wire 契約(protobuf)の変更。

## 受入基準

- 明示指定が無い限り、ストリーミング VC の入力・出力デバイス、および発話系の録音・再生デバイスは、いずれもそのデバイスのネイティブレートで開かれる。
- 4 つのデバイスそれぞれについて、開くレートを設定で明示指定でき、未指定なら自動的に決まる。
- 自動で決められない場合は起動時に明確に失敗し、どの設定項目を指定すべきかが示される。
- 解決したレートで実際にデバイスを開けないことが、起動時に検出される。
- 実際に開いたレートと、その決定根拠がログに残る。
- デバイスを開くレートと、そのデバイス境界を流れる音声のレートが一致する場合は変換が行われず、本変更の前後で出力がビット単位で一致する。
- サンプルレート変換の阻止域減衰と通過帯平坦性が、自動テストで数値として検証される。
- 連続入力をブロックに分割して逐次変換した結果が、同じ入力を一括変換した結果と一致する(ブロック境界に不連続が生じない)。
- 変換によってストリーミング経路に生じる追加遅延が、1 ブロック分まるごとの遅延にならない。
- 変換で振幅が表現可能な範囲を超えた場合、ラップアラウンドせず飽和する。
- 1 発話ぶんの音声を変換したとき、末尾が欠けない。
- 発話系の再生で、音声ソースのサンプルレートが変わってもデバイスは開き直されない。
- 発話系の録音で、無音判定と録音区間長の時間換算が実時間の秒数と一致する。
- 下流(音声認識・VC・字幕)が受け取る音声のサンプルレートは、本変更の前後で変わらない。
- 依存パッケージが追加されない。
- ストリーミング VC の consumer ロールが、torch を導入しない環境で従来どおり動作する。
