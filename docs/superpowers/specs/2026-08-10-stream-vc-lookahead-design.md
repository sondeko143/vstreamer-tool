# streaming VC の右文脈(lookahead)を設定可能にする

## 問題

streaming VC の変換品質はバッチ経路(発話単位の変換)に届いていない。その差のうち構造的に支配的
なのが、出力サンプル 1 個あたりにモデルが見ている「未来の文脈」の少なさである。

既定構成(ブロック 160ms / 左文脈 500ms / クロスフェード 25ms / SOLA 探索 5ms)で幾何を実測する
と、emit は入力ブロックの相対時刻 **[-50, +110]ms** を覆う。すなわち emit 開始点には 450ms の
左文脈がある一方、emit 終端より後ろに残る右文脈は **30ms しかない**。HuBERT/ContentVec は窓全体
に attention を張る双方向モデルなので、この非対称はそのまま表現の質に効く。バッチ経路が発話全体
を両側文脈として持つのと比べたときの品質差の主因はここにある。

右文脈は遅延と引き換えでしか増やせない。にもかかわらず、その交換比率を運用者が選ぶ手段が現在は
無い。クロスフェード帯を伸ばせば副作用として右文脈も増える(実測: 25ms → 70ms で右文脈 30ms →
75ms)が、同時に「二つの別描画の和」である帯の割合が全出力の 15.6% から 43% へ比例して広がる。
その帯は SOLA で位相を合わせてなお相関 0.82 の無相関成分を含むため、品質のために使うノブとして
は筋が悪い。

さらに、どれだけ右文脈を足せば品質がどれだけ戻るのかを測る手段も無い。既存の実測ハーネスは
速度(RTF)しか測らず、変換結果をバッチ経路と比較していない。既定値を実機の試聴だけで決めようと
して決め切れなかった前例(入力エンベロープの整形指数。実測は明確な差を示したが耳では判別できず、
既定を動かせないまま据え置かれている)があるため、数値と試聴素材の両方が要る。

## ゴール

- 右文脈の量を設定で調整できるようにする。
- その調整が左文脈を痩せさせないようにする。
- 既定では導入前と同一の音が出るようにする。
- 右文脈を増やしたときに品質がどれだけバッチ経路へ近づくかを、数値と試聴素材の両方で確認できる
  ようにする。
- 右文脈を増やした代償(遅延と計算量)が、運用者と測定者の両方から見えるようにする。

## 非ゴール

- 既定値そのものの決定。実機での測定と試聴で決めるため、この作業では右文脈を増やさない状態を
  既定のまま据え置く。
- ブロック長を縮めて合計遅延を据え置いたまま右文脈を稼ぐ経路。推論レートが倍になるうえ、短い
  ブロックは seam のクリックを理由に一度却下されているため、独立に評価する。
- クロスフェードのフェード則と SOLA 探索の見直し。
- バッチ経路(発話単位の変換)の挙動変更。
- 出力段の再量子化の削減、入出力のサンプルレート変換をアプリ内に取り込むこと、音声デバイスの
  バッファ量を設定可能にすること。いずれも品質観点で別途挙がっているが、右文脈とは独立に評価
  できる。
- 一時停止・デバイス再接続の直後に左文脈がゼロから立ち上がることへの対策。
- f0 抽出器の既定変更、および f0 の外れ値平滑化。

## 受入基準

- [ ] 右文脈の量を設定で指定でき、指定した量だけ実際に増える。
- [ ] 右文脈を増やしても、emit 開始点で使える左文脈の量は増やす前と変わらない。
- [ ] 右文脈を増やしても 1 ブロックあたりの出力サンプル数は変わらず、出力デバイスに対する
      レートロックが保たれる(時間ドリフトも sink の飢餓も起きない)。
- [ ] 右文脈を増やさない既定の設定では、出力が導入前とビット単位で同一である。
- [ ] 右文脈を増やすと、片道遅延がちょうどその量だけ増える。
- [ ] VAD ノイズゲートと入力エンベロープのゲイン曲線が、右文脈をどれだけ増やしても出力へ正しく
      時間整列し、ブロック境界にゲインの段差を作らない。
- [ ] 右文脈の量をどれだけ大きくしても、それ自体が原因で起動時の設定検証や初期化に失敗する
      ことはない。
- [ ] 起動時のログから、解析窓の長さ・出力の遅延量・右文脈によって増えた遅延量が読み取れる。
- [ ] 同一の入力音声に対し、右文脈の量を変えた複数の変換結果とバッチ経路による変換結果とを
      比較した数値の表が、1 回の実行で得られる。
- [ ] その表から、右文脈の量ごとの計算コストの変化が読み取れる。
- [ ] 同じ実行から、各設定の変換音声が試聴できる形で得られる。
- [ ] 設定例と決定記録の記述が、実装と一致している。
