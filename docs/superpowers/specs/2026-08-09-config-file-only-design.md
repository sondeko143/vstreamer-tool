# config をファイル1本に統一する

## 問題

config の入力経路が `--config` ファイルと環境変数の2本ある。環境変数側は pydantic-settings の
`BaseSettings` に依存しているが、使っている機能は `env_prefix` と `env_nested_delimiter` の2つだけ
にもかかわらず、pydantic-settings は AWS / Azure / GCP Secret Manager・CLI・dotenv・YAML など全
プロバイダを無条件に import する。実測（2026-08-09）では、pydantic-settings を単体で import
した場合の増分が **+13.7 MB RSS / +176 modules / 起動 +473 ms** で、これは起動時にロードされる
アプリ中核（60 MB / 約 1.0 s）の中で単一としては pydantic 本体より大きい。ただし実際のパイプライン
起動経路では grpc / google-cloud 系が既に多くを import 済みのため、pydantic-settings 固有の
削減量は実測で 32 modules / 約 1.6 MB にとどまった。

その環境変数経路の実質的な唯一の利用者はコンテナ配備（イメージの起動コマンドが `--config` を
渡していない）だが、その配備はすでに機能していない。エディタのクラウド実行構成は最終更新が
2023-05-28 で、2026-07-26 に削除済みのモジュールをいまだに参照している。環境変数経路を覆う
テストは1件もなく、利用者向けの案内文書にも記載がない。

経路が2本あること自体にも実害がある。設定を明示せずに構築したテストが、開発者の環境変数を
拾いうる状態になっている。

## ゴール

- config の入力経路を `--config` ファイル1本に統一する。
- 使われていないコンテナ配備の経路を、それを支えるためだけに存在する設定ごと撤去する。
- 設定ファイルの打ち間違いが従来どおり起動時に検出される状態を維持する。

## 非ゴール

- pydantic 本体および gRPC のロード量削減。いずれも調査済みで、config スキーマと transport
  そのものであり削減しないと判断した。
- 環境変数に代わる新しい設定注入手段の追加。
- `PORT` キーによる待受ポート指定の維持。これはクラウド配備の契約のためだけに存在していた。
- `vsctl` の接続先を与える環境変数への変更。これは config とは無関係。
- セクション内（ネストされた設定）の未知キーを弾くようにすること。現状もトップレベルしか
  検査しておらず、これを厳格化すると既存の設定ファイル次第で起動しなくなる。今回は現状の
  検査範囲をそのまま維持する。
- Linux で動かす経路を別途用意すること。

## 受入基準

- [ ] `--config` を指定せずにパイプラインを起動しようとすると、使用法エラーを表示して非ゼロ終了する。
- [ ] 環境変数で設定値を与えても、起動した pipeline の設定には反映されない。
- [ ] 設定ファイルのトップレベルに未知のキーが含まれていると、起動時に検証エラーで失敗する。
- [ ] 既存の設定ファイルが、これまでと同じ設定値に解決される。
- [ ] pydantic-settings がプロジェクトの依存から外れ、パイプライン起動時にロードされるモジュール
      にも含まれない。
- [ ] リポジトリに、コンテナイメージの定義・そのための依存エクスポート成果物・エディタの
      クラウド実行構成が残っていない。
- [ ] 依存解決の対象プラットフォームが Windows のみになっている。
- [ ] 設定を明示せずに構築したテストが、開発者の環境変数に影響されない。
- [ ] 設定の入力経路についてのリポジトリ内の記述が、実装と一致している。
