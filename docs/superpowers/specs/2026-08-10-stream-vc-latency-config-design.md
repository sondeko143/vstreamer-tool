# ストリーミング VC の latency を設定値にする

## 問題

`stream_vc` の入力ストリーム(マイク capture)と出力ストリーム(playback / consumer)は、どちらも PortAudio へ要求する latency を `"low"` に固定している。

`"low"` が実際に何秒になるかはホスト API とデバイスに依存し、桁が変わる。低すぎるデバイスでは overflow / underflow が定常的に出て、間引かれた警告と telemetry だけが積み上がる。逆に高すぎるデバイスでは、ブロック長を詰めても取り返せない遅延が乗る。どちらもコードを書き換えないと対処できない。

さらに、入力と出力は別デバイス(role を分ければ別マシン)なのに、片側だけ緩めるという当たり前の調整ができない。

観測性の面でも、開いたストリームが結局何秒で開いたのかがログに出ない。要求した `"low"` が実際にどう解決されたかを見ずに他の遅延パラメータを詰めることになる。

## ゴール

- 入力側と出力側の latency を、設定ファイルから独立に指定できる。
- デバイス既定の低遅延 / 高遅延に加えて、明示の秒数も指定できる。
- 設定を書かなければ、従来と同じ latency でストリームが開く。
- 開いたストリームが実際に得た latency がログから読める。

## 非ゴール

- 発話経路 `[recording]` / `[playback]` のストリーム。これらは latency を要求しておらず PortAudio 既定に任せている。今回は触らない。
- 実測に基づく latency の自動選択・自動チューニング。
- `block_ms` / `context_ms` / `jitter_buffer_ms` など既存の遅延パラメータの変更。
- ホスト API の選択、WASAPI 排他モードなど PortAudio の他の設定項目の露出。

## 受入基準

- 設定を書かない場合、入力・出力とも従来と同じ latency 要求でストリームが開く。
- 入力側だけ、または出力側だけ latency を変更でき、他方は影響を受けない。
- latency として「デバイス既定の低遅延」「デバイス既定の高遅延」「明示の秒数」の 3 通りを指定でき、いずれもそのままデバイスへの要求として渡る。
- 不正な値(未知の文字列、0 以下の数値)は起動時に fail-loud で拒否され、設定ファイル由来の他の問題と同じ形で報告される。
- ストリームを開いたときのログに、要求した値と実際に得られた latency の両方が出る。
- `role=producer` は入力側の設定だけを、`role=consumer` は出力側の設定だけを使う。
- 設定例ファイルに、両方の項目と取りうる値が記載されている。
- 既存のテストが全て緑のまま。
