# GUI: 走っている pipeline へのリモート操作パネル 設計

## 問題

GUI は多 pipeline マネージャとして、pipeline の生成・config 編集フォーム・起動前 readiness・サブプロセス起動/停止まで抱えている。しかし実運用の形はそうなっていない。

1. pipeline は複数マシンに分散して**すでに走っている**（録音マシン、GPU マシン、再生マシン）。GUI が扱えるのは自分のマシンで自分が起動したものだけで、別マシンで走っている pipeline には何もできない。
2. 走っている pipeline に対してやりたいのは「届いているか」「止める / 再開する」「config を読み直させる」だけで、それらは今の GUI に無い。
3. 使わない層（config フォーム・レシピ・readiness・共有パス伝播・profile と migration）が config スキーマに結び付いているため、設定を足すたびに GUI 追随のコストだけが発生する。

## ゴール

- 走っている pipeline の宛先（ホストとポート）を指定して、そこへ届いているかを確認できる。
- 指定した宛先の pipeline を pause / resume できる。
- 指定した宛先の pipeline に config を読み直させることができる。
- よく使う宛先は覚えていて、開いた直後から操作できる。
- 操作の成否と、失敗したときの理由が画面上で分かる。
- 応答しない宛先を選んでも操作は有限時間で終わり、GUI は固まらない。

## 非ゴール

- GUI からの pipeline 起動・停止、config 編集、起動前 readiness 表示（いずれも GUI の役目から外す）。
- データイベント（テキスト投入や音声送出）の送信。操作パネルであって pipeline に仕事を流し込むものではない。
- `set_filters` / `forward` など、上記 3 操作以外の制御イベント。
- 対象マシンのファイルシステムの参照・補完。reload のパスは対象側が解決する。
- 認証・暗号化・宛先の到達性以外の健全性診断（pause 中かどうかの問い合わせなど）。
- 既存の pipeline 設定ファイル群（`default.toml` / `pipelines.toml` / `pipelines/*.toml`）の移行や削除。

## 受入基準

- [ ] 宛先を指定して疎通確認でき、到達できたか否かと往復時間が分かる。
- [ ] 宛先を指定して pause / resume でき、対象の pipeline が実際に停止・再開する。
- [ ] 宛先を指定して reload でき、対象が指定された config を実際に読み直す。
- [ ] 登録した宛先は GUI を閉じても残り、次回起動時にそのまま使える。
- [ ] 失敗したとき、到達できなかったのか対象側で失敗したのかが理由付きで示される。
- [ ] 応答のない宛先へ送っても操作は有限時間で打ち切られ、その間も GUI は操作を受け付ける。
- [ ] 宛先の保存ファイルが壊れていても GUI は起動し、宛先を入れ直せる。
- [ ] reload に必要な情報が欠けたまま送信されない。
