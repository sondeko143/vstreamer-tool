# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

VStreamer Tool is a real-time speech pipeline for live streaming. It chains recording → transcription → translation → subtitles → text-to-speech → voice changing → playback, integrating external services (AmiVoice ACP, Google Cloud Speech/Translate, Whisper, VOICEROID2, VOICEVOX, RVC). The package name is `vspeech` (the project is `voicerecog` in `pyproject.toml`); a separate `cli/` package provides `vsctl`, a command that remote-controls pipelines which are already running.

## Commands

This project uses **uv** (migrated from Poetry). Python **3.14 only** (`>=3.14,<3.15`).

```sh
# Install. Base = transcription/subtitle only; add extras for other subsystems.
uv sync
uv sync --extra audio       # recording/playback (sounddevice; PortAudio ships in the wheel)
uv sync --extra whisper     # faster-whisper; GPU run needs a host CUDA 12 toolkit for ctranslate2 (ADR-0039)
uv sync --extra vroid2      # VOICEROID2 TTS
uv sync --extra voicevox    # VOICEVOX TTS
uv sync --extra rvc         # RVC voice changer (a lone --extra deselects the others; prefer 'uv sync --all-extras')
# NB: rvc (and therefore --all-extras) downloads 1,027MiB of NVIDIA CUDA-runtime wheels
# (6 wheels, sizes summed from uv.lock), 1,481MiB once unpacked into site-packages/nvidia/.
# onnxruntime-gpu bundles no CUDA, so these are the only supplier (ADR-0083).

# Run the pipeline (gRPC server + workers)
uv run python -m vspeech --config ./config.toml

# Control a pipeline that is ALREADY running, here or on another machine.
# No extra needed — vsctl adds no dependencies. Also runnable as `python -m cli`.
uv run vsctl ping --to 192.0.2.10:8080     # 疎通確認; exit 0 = reachable
uv run vsctl pause --to 192.0.2.10:8080    # also: resume
uv run vsctl reload --to 192.0.2.10:8080 --config-path D:/vstreamer/config.toml
VSPEECH_TARGET=192.0.2.10:8080 uv run vsctl resume   # --to's default

# Tests
uv run pytest                              # all tests
uv run pytest tests/test_shared_context_routing.py   # one file
uv run pytest tests/test_shared_context_routing.py::test_worker_output_remotes  # one test

# Lint / format / type-check (ruff + ty are dev dependencies; both from Astral)
uv run ruff format .
uv run ruff check .
uv run ty check            # type checker (replaced pyright)
```

Dev tasks are consolidated under **poethepoet**: `poe_tasks.toml` is the single source of task definitions (`pyproject.toml` only pulls it in via `[tool.poe] include`). Run `uv run poe` to list tasks, `uv run poe <task>` to run one. The former `Makefile` is retired — its `voicevox-assets` target is now a poe task, and its `requirements-pod` / `clean` targets went away with the container deploy (ADR-0067).

`config.toml.example` documents every setting; `vspeech/config.py` is the source of truth for defaults and shapes. Config files (`config*.toml`, `config*.json`, `key.json`, `*.log`, `*.wav`) are gitignored.

Review findings deliberately deferred out of a branch's scope are recorded as comments **at the code they concern** — each with the reason it was deferred — not in a separate tracking doc, so the note surfaces for whoever next touches that code. (A former `docs/follow-ups.md` did the opposite and drifted out of sync with the code; don't recreate it.)

**Docs are a 3-doc model** — keep each layer thin and in its lane:
- **spec** ([`docs/superpowers/specs/`](docs/superpowers/specs)) is **thin**: exactly the four sections 問題 / ゴール / 非ゴール / 受入基準. 受入基準 are observable conditions that stay true after implementation — no function/file names, no how. A spec must not accumulate architecture, config schemas, test plans, or decision rationale; those go elsewhere. This keeps specs from going stale as the code moves.
- **ADR** ([`docs/adr/`](docs/adr), see its [README](docs/adr/README.md) index) is the **immutable decision layer**: one decision per file (`NNNN-kebab-title.md`), Nygard-lite (Context / Decision / **Alternatives rejected** / Consequences / Status) per [`docs/adr/template.md`](docs/adr/template.md). Anything with a rejected alternative, a hard-to-reverse choice, a boundary/contract change, or a non-trivial default/threshold belongs here. Never rewrite an ADR to reverse it — supersede it with a new one and flip the old Status to `Superseded by [ADR-NNNN]`.
- **plan** ([`docs/superpowers/plans/`](docs/superpowers/plans)) is **disposable**: steps, affected files, tests. It goes stale after implementation by design — don't sync it back.

When you change something with a decision layer, add or supersede an ADR (bump the README index); when a spec's rationale/impl would grow it past four sections, route it to the ADR/plan instead. The `create_session` / Silero-VAD invariant below is recorded as [ADR-0024](docs/adr/0024-onnx-session-single-factory.md); `ty` replacing pyright is [ADR-0012](docs/adr/0012-adopt-ty-type-checker.md).

Every GPU-capable `onnxruntime` session (RVC decoder, HuBERT, RMVPE) is opened through the one `create_session` in [`vspeech/lib/onnx_session.py`](vspeech/lib/onnx_session.py). It honours the caller's `Device` (the torch-free value type in [`vspeech/lib/cuda_util.py`](vspeech/lib/cuda_util.py), mirroring `torch.device`'s `type`/`index`), and decides whether to request the CUDA EP from **onnxruntime's own `get_available_providers()`** — never from another framework's view of the GPU, and never build a second copy of the factory: the provider guard then only ever gets fixed in one of them. Silero VAD (`vspeech/lib/vad.py`) is the deliberate exception — it pins `CPUExecutionProvider` and takes no device. `tests/lib/test_onnx_session.py` enforces both, asserting `InferenceSession(...)` is constructed in exactly those two files. That same factory is also where the **CUDA runtime** is loaded: `onnxruntime-gpu`'s wheel bundles no CUDA, and with torch gone the only supplier left is the pinned `nvidia-*` wheels, so `create_session` calls `onnxruntime.preload_dlls(directory=...)` once per process before the first GPU session ([ADR-0083](docs/adr/0083-cuda-runtime-from-nvidia-wheels.md)) — `directory=` is not optional, because onnxruntime 1.27's own default paths predate the CUDA 13 wheel layout.

The runtime is torch-free end to end — the device layer since [ADR-0078](docs/adr/0078-torch-free-device-resolution.md), the RVC conversion path since [ADR-0080](docs/adr/0080-torch-free-rvc-runtime.md). GPUs are enumerated through the CUDA driver API (`nvcuda.dll` via ctypes, in [`vspeech/lib/cuda_driver.py`](vspeech/lib/cuda_driver.py)) rather than NVML, because the ordinal it yields is handed straight to ctranslate2's `device_index` and the CUDA EP's `device_id`, which speak the CUDA ordinal space. RVC's tensor plumbing is numpy plus onnxruntime's own `OrtValue` ([ADR-0081](docs/adr/0081-ort-native-value-binding.md)) and its resampling is the in-house polyphase FIR ([ADR-0082](docs/adr/0082-rvc-resample-on-inhouse-polyphase.md)), so **`torch` and `torchaudio` are not installed at all**. **No test enforces that by name** ([ADR-0087](docs/adr/0087-weight-guarded-by-measurement-not-named-bans.md) superseded ADR-0084 and ADR-0086 and deleted `tests/test_forbidden_imports.py` outright): what this project wants to stop is an unintended *performance regression*, not the presence of a particular package, and a deny-list of names has no principled membership rule — it grows without limit and its recorded justifications rot unnoticed, both of which were demonstrated by measurement. So `uv add torch` stops no test today. It is caught when it shows up as **weight**, on the measured paths described below — and it does show up, because `ctranslate2` (a core dependency) grabs torch with `try: import torch` whenever it is present, so the transcription worker pays 477MB and 3.2s again the moment torch is installed, whether or not a line of this repo imports it. That worker's path is measured for exactly this reason. The only place torch is supplied is the offline ONNX-generation poe tasks' `uv run --with` overlay (`convert-hubert`, `export-hubert-onnx`, `export-fcpe-onnx`). Everything else that can use torch merely *tolerates* one you installed yourself: `poe stream-vc-baseline --seed-mode both` has no overlay and exits with an actionable message without it, and the two tests that gate on it (`tests/scripts/test_export_hubert_onnx.py`, `tests/lib/test_pitch_extract_fcpe.py`) skip. Nothing drags it back in. fp16 capability comes from the device's compute capability, not its product name ([ADR-0079](docs/adr/0079-fp16-by-compute-capability.md)).

The runtime's **weight** is gated on the outcome rather than on a list of names ([ADR-0085](docs/adr/0085-gate-runtime-weight-on-outcome.md), widened by [ADR-0087](docs/adr/0087-weight-guarded-by-measurement-not-named-bans.md)), and since ADR-0087 this is the **only** protection the project has against a dependency getting heavy again. `tests/test_runtime_footprint.py` imports each of eleven **measured paths** in a pristine child process and checks what that loads — the set of top-level modules, the module count, and the working set — against `tests/runtime_startup_baseline.json`, which `scripts/runtime_startup_baseline.py` records (`uv run poe runtime-baseline --update --runs 10`; startup *time* is measured and printed but deliberately never gated, because it is too noisy). The paths are `MEASURED_PATHS` in that script, and they are the whole value of the gate: `vspeech.main` alone measures almost nothing, because every worker is imported lazily inside `vspeech_coro` and the transcription worker defers `faster_whisper` — and so `ctranslate2`, and so any installed torch — one step further into a function body. Weight landing there makes every running pipeline heavier while the entry point stays exactly as light as before. So each path names the module chain a *running* worker reaches, deferred imports included, and carries a `reaches` list of what it must load for its coverage claim to hold — a path that quietly stops loading its heavy dependency fails rather than looking like coverage. **Adding a worker or a startup path means adding it to `MEASURED_PATHS`**; unmeasured weight is undetected weight, and that check is mechanical (is it a chain a running pipeline executes?) rather than a judgement call. Deliberately out of scope: anything needing a GPU, model assets or a config file — `uv run poe vc-footprint` measures a real warmed pipeline on demand for that. When the gate fires for a legitimate reason — a new dependency on a measured path, or a routine upgrade that renames a build-id-bearing entry such as charset_normalizer's `81d243bd2c585b0f4821__mypyc` — re-record with that command and **review the diff it produces**. Never hand-edit the JSON, and never re-record to silence a change you have not read: a re-record is the fastest way to turn any snapshot gate green, and the record's own checks (enough runs, every measured path present, and a calibration proving the memory headroom still catches numpy) cannot tell a legitimate re-record from one taken on a bloated tree.

A **gitleaks pre-commit gate** ([`.gitleaks.toml`](.gitleaks.toml), [`.pre-commit-config.yaml`](.pre-commit-config.yaml)) scans staged changes for secrets **and** environment-PII (private LAN IPs, `C:\Users\<name>` paths, AmiVoice `appkey`). It is local-only; activate with `uv tool install pre-commit && pre-commit install` plus a `gitleaks` binary on PATH. Use `<USER>`/`<NAS_HOST>` placeholders for machine-specific paths/hosts in committed docs. See [docs/secret-scanning.md](docs/secret-scanning.md).

### HuBERT assets (RVC only, offline)

The RVC content encoder runs as ONNX. Its assets are derived, gitignored, and built by two
one-shot offline steps whose dependencies — **torch included, since [ADR-0080](docs/adr/0080-torch-free-rvc-runtime.md)** — live
**only** in the poe task's `uv run --with` overlay, never in `pyproject.toml` or `uv.lock`:

```sh
# hubert_base.pt -> hubert_contentvec/ (transformers asset). Needs fairseq, so it runs in a
# throwaway 3.11 environment. Keep ~/.config/vstreamer/hubert_base.pt: it is the input.
uv run poe convert-hubert --input ~/.config/vstreamer/hubert_base.pt \
    --output ./hubert_contentvec --golden ./hubert_golden

# hubert_contentvec/ -> hubert_fp32.onnx + hubert_fp16.onnx. Self-verifies against the
# golden and exits non-zero if the gate fails, in --measure-only too. The fp16 graph is
# exported on CUDA, so this overlay names a CUDA torch wheel by URL — `[tool.uv.sources]`
# does not reach `--with`, and PyPI's Windows torch is CPU-only. Its fp16 verification
# session asks onnxruntime for a ~10GB buffer, so make a card with that much VRAM be
# cuda:0 first (PowerShell): $env:CUDA_VISIBLE_DEVICES = "<ordinal>"  # 8GB is not enough
uv run poe export-hubert-onnx --asset ./hubert_contentvec --golden ./hubert_golden
```

`rvc.hubert_model_file` points at the **asset directory**, not a file. The runtime opens only
`hubert_*.onnx` + `mapping.json`; `vspeech/` never imports `fairseq` or `transformers`. That
is a property of the code, not a ban: since [ADR-0087](docs/adr/0087-weight-guarded-by-measurement-not-named-bans.md)
no test names a package in order to forbid it, and what would catch either of them coming
back is the weight they add to a measured path. Never run `uv sync --extra rvc` — it
uninstalls the other extras. Use `uv sync --all-extras`.

## Architecture

The system is an **event-driven graph of asyncio workers** connected by queues and a gRPC transport. There are no direct calls between workers — they are wired together only by `EventType` and routing chains.

### Process startup (`vspeech/main.py`)
`vspeech_coro` opens an `asyncio.TaskGroup` and conditionally spawns one task per enabled subsystem (gated by `config.<section>.enable`). Two infrastructure workers always run: `receiver` (gRPC server) and `sender` (gRPC client + local dispatcher). Workers are lazily imported so optional dependencies aren't required unless their feature is enabled. Shutdown propagates as a `WorkerShutdown` exception group caught with `except*`.

### The routing model (`vspeech/lib/command.py`, `vspeech/shared_context.py`)
This is the core abstraction and the part that requires reading several files to understand:

- External input arrives as a protobuf `Command` (from the `vstreamer-protos` dependency) containing **chains** — ordered lists of operations describing a pipeline (e.g. `transcription → translation → subtitle`).
- A `Command` is exploded into `WorkerInput`s, each with a `current_event` (the step to run now) and `following_events` (the remaining graph). `EventType` ↔ protobuf `Operation` conversion lives in `command.py` (`event_to_operation` / `operation_to_event`).
- A worker consumes a `WorkerInput`, does its job, and emits a `WorkerOutput` carrying `text` and/or `sound` plus the unprocessed `followings`. It puts this on `context.sender_queue`.
- The **sender** inspects each following step's `remote`: empty remote → dispatched locally via `process_command` (pushed onto the target worker's `in_queue`); non-empty remote → serialized back to a `Command` and sent over gRPC to another VStreamer instance. This is how pipelines span machines.
- `EventAddress.from_string` parses route strings of the form `<endpoint_uri>/<event_name>?<queries>` (e.g. `//host:8080/translation?t=en`). Query params have short aliases defined in `Params` (`t`=target_language, `s`=source_language, `p`=position, `i`=speaker_id, `v`=volume, `spd`=speed, `pit`=pitch). `EventType.from_string` also accepts shorthands (`sub`, `transc`, `transl`, `rec`, `play`, `fwd`).
- Pipelines are seeded two ways: the `recording` worker builds the initial `WorkerOutput` from `config.recording.routes_list` (`WorkerOutput.from_routes_list`), and inbound gRPC `Command`s arrive with their own chains.

### Control events vs. data events
Beyond data events (transcription/translation/subtitle/tts/vc/playback/recording), `process_command` handles control events synchronously: `pause`/`resume` toggle the global `context.running` `asyncio.Event` (a gate all workers respect), `reload` re-reads the config file and flags affected workers, `set_filters` swaps the text-replacement filters at runtime, `forward` re-emits text to its followings, and `ping` is a health check.

### Worker pattern
Every worker in `vspeech/worker/` follows the same shape:
- `async def <name>_worker(context, in_queue, out_queue)` — a loop that reads `in_queue`, processes, and puts results on `out_queue` (almost always `context.sender_queue`). It wraps `CancelledError` with `shutdown_worker(e)` so cancellation surfaces as `WorkerShutdown`.
- `def create_<name>_task(tg, context)` — registers the worker via `context.add_worker(event, configs_depends_on=[...])` and creates the task named after its `EventType`.

`configs_depends_on` lists the config sections a worker cares about; on a `reload` event, `process_command` compares old vs. new values and sets `need_reload` only for workers whose dependencies changed. Workers check `context.need_reload` mid-loop to rebuild clients/models (e.g. the transcription worker picks a different backend via `worker_type`). The `transcription`, `tts` and `subtitle` workers dispatch to sub-implementations by `worker_type` (ACP/GCP/WHISPER, VR2/VOICEVOX, TK/OBS) — add new backends there. The `subtitle` OBS backend talks to OBS as an obs-websocket client and pushes both text and style. Its backends live in separate modules (`worker/subtitle_tk.py`, `worker/subtitle_obs.py`) behind a dispatcher that imports neither at module level, so **`tkinter` is imported only by the TK backend** and an OBS pipeline runs headless — that split is the point of [ADR-0040](docs/adr/0040-subtitle-obs-backend-via-worker-type.md), not a side effect of the transport ([0040](docs/adr/0040-subtitle-obs-backend-via-worker-type.md) through [0043](docs/adr/0043-obs-websocket-client-in-house.md)).

### `cli/` = remote control only (`vsctl`)
The `cli/` package is a remote control for pipelines that are **already running**, here or on another machine ([ADR-0061](docs/adr/0061-remote-control-as-cli.md), which replaced the GUI it superseded in [ADR-0060](docs/adr/0060-gui-remote-control-panel.md) — that in turn superseded ADR-0032/0033/0045/0046). It sends exactly four control events over gRPC — `ping` (疎通確認) / `pause` / `resume` / `reload` — one per process invocation. It does **not** launch pipelines, edit config, or evaluate readiness, and it stores nothing: the target is `--to HOST:PORT` (default from `$VSPEECH_TARGET`). Consequently `cli/` depends only on `EventType` and `EventAddress`, never on the `Config` schema — keep it that way, and keep its dependency footprint at zero (`click`/`grpcio` are already core deps; the old `gui` extra's ttkbootstrap/pillow/platformdirs are gone). Four traps worth knowing: build Commands through `EventAddress.to_pb()`, never protobuf `PAUSE`/`RESUME` directly, so the `EventType` ↔ `Operation` mapping stays in one place; `reload`'s `file_path` is opened by the **receiving** machine, so never resolve or validate it locally; every RPC needs a deadline, and the target needs a port (gRPC silently waits out the deadline on `host` without `:port`); and the entry point must force stdout/stderr to UTF-8 before click prints anything, or Japanese help text kills `vsctl --help` on a cp932/cp1252 console (`tests/cli/test_entrypoint.py` guards this — CliRunner cannot catch it). `vspeech/preflight.py` is unaffected — it still fails loud at startup ([ADR-0038](docs/adr/0038-worker-config-preflight-fail-loud.md)), which is now the only place config problems surface.

### `SharedContext`
The single shared object threaded through everything: holds the live `Config`, the `running` gate, the `sender_queue`, and the `workers` registry (`dict[str, WorkerMeta]`, keyed by event name, each owning its own `in_queue`). `put_queue(dest_event, request)` is how the local dispatcher routes work to a worker.

## Conventions & gotchas

- **Pydantic v2** (`pydantic>=2,<3`). Code uses v2 APIs: `model_config = ConfigDict(...)`, `model_validate`, `model_dump`, `model_dump_json`, `model_validator(mode="after")`, `field_serializer`, `populate_by_name`, `from_attributes`, `AliasChoices`, `SecretStr`. `pydantic-settings` is not a dependency ([ADR-0066](docs/adr/0066-config-input-file-only.md)); nothing imports `BaseSettings` or `SettingsConfigDict`. SecretStr secrets that must serialize to plaintext JSON (so a JSON config round-trips through `--config x.json`; the original driver, a GUI→main handoff, is gone as of [ADR-0061](docs/adr/0061-remote-control-as-cli.md)) use `@field_serializer(..., when_used="json")` — note `json_encoders` does NOT affect `model_dump_json()` for SecretStr in v2. Do **not** reintroduce v1 APIs (`parse_obj`/`.dict()`/`.json()`/`root_validator`/`orm_mode`/`Field(env=)`/`json_encoders`). To enumerate a model's field names, use `type(x).model_fields` (class access — instance access is deprecated in 2.11+), **never** `get_type_hints(instance)` or `instance.__annotations__`: on a v2 *instance* both are empty (`{}`), which silently made `VR2.load_voice` apply zero VOICEROID2 params after the migration.
- **Config loading** (`Config` in `config.py`): from a **required** `--config` file (TOML, or JSON if the name ends in `.json`) and nothing else — the environment-variable path and its pydantic-settings dependency were removed in [ADR-0066](docs/adr/0066-config-input-file-only.md), so `python -m vspeech` with no `--config` is a usage error. `Config` sets `extra="forbid"` explicitly (it used to inherit it from `SettingsConfigDict`); note this guards the top level only. Secrets (`ami.appkey`, `gcp.service_account_info`) are `SecretStr`.
- **Comments and docstrings are written in English; text a user reads stays Japanese** ([ADR-0064](docs/adr/0064-code-comments-in-english.md)). Write every new `#` comment and docstring in English. Deliberately Japanese, because their reader is not reading the code: log and exception messages, `config.py` `description=`, argparse `help=`/`description=`/`epilog=`, click `help=` strings **and click command docstrings** (those *are* the `vsctl --help` body), Japanese test fixtures and the assertions that check Japanese wording. Prose docs (ADR/spec/plan/`README.md`) stay Japanese too — the rule is about code, not documentation. A bulk pass converted 84 files; `tests/lib/test_obs_ws.py`, `tests/lib/test_vad.py` and `tests/lib/test_log_throttle.py` still have Japanese comments. **Don't sweep them separately — when you edit a file that still has Japanese comments, translate that file's comments in the same change.** That a diff touches only comments/docstrings is machine-provable: compare `ast.dump()` of HEAD vs. the working tree with docstrings stripped (comments never reach the AST).
- **Imports are one-per-line** (`ruff` `force-single-line = true`) and auto-sorted on save. Type checking is **ty** (Astral, configured under `[tool.ty.environment]`, Python 3.14) — the project migrated off pyright. Custom type stubs live in `typings/`.
- **Platform constraints** (encoded in `pyproject.toml`): `pyvcroid2` is a **Windows-only** wheel pinned in `[tool.uv.sources]`, and `voicevox-core` is pinned there to the single `win_amd64` wheel; the per-platform `marker`ed list existed only for the Docker image and went away with it ([ADR-0067](docs/adr/0067-drop-container-deploy-path.md)). The `torch`/`torchaudio` pins and the PyTorch cu130 index went with [ADR-0080](docs/adr/0080-torch-free-rvc-runtime.md): `torch`, `torchaudio`, `faiss-cpu` (nothing ever imported it), `fairseq`, `transformers` and `torchfcpe` are **not** runtime dependencies and are absent from both `pyproject.toml` and `uv.lock` — the HuBERT content encoder runs as ONNX, and the three offline tools (`poe convert-hubert` / `poe export-hubert-onnx` / `poe export-fcpe-onnx`) supply what they need from a `uv run --with` overlay (see *HuBERT assets*). What the rvc extra does carry for the GPU is the CUDA runtime itself, as four named `nvidia-*` wheels ([ADR-0083](docs/adr/0083-cuda-runtime-from-nvidia-wheels.md)); `onnxruntime-gpu[cuda,cudnn]` cannot resolve them, so they are pinned by hand. Dev and deploy target is Windows only — `[tool.uv] environments` resolves for `sys_platform == 'win32'` alone since [ADR-0067](docs/adr/0067-drop-container-deploy-path.md) removed the Linux container image. The CPU `onnxruntime` is force-overridden out (`override-dependencies`) because it clobbers `onnxruntime-gpu`'s CUDA binary — both expose the same `onnxruntime` module. `voicevox-core` is pinned to **0.16.4** (`cp310-abi3`, pydantic-free). Its ONNX Runtime, OpenJTalk dictionary, and `.vvm` voice models are **not** bundled in the wheel — fetch them with the VOICEVOX downloader (`uv run poe voicevox-assets`) and point `voicevox.openjtalk_dir` / `model_dir` / `onnxruntime_path` at them. VOICEVOX uses its own `voicevox_onnxruntime` build, distinct from the `onnxruntime-gpu` used by whisper/rvc; set `onnxruntime_path` explicitly so the correct DLL is loaded.
- **Version-specific features in use**: `TaskGroup` and `except*` exception groups (3.11+); PEP 695 `type X = ...` aliases and `class C[T]` type parameters (3.12+, required by ruff's `UP040`/`UP046`). The floor is **3.14** (`requires-python = ">=3.14,<3.15"`), reached by a phased migration off 3.10 — numpy 2, then CUDA 13, then 3.14 itself ([ADR-0025](docs/adr/0025-target-python-314-phased.md) through [0031](docs/adr/0031-audio-pyaudio-to-sounddevice.md)). The former 3.13/3.14 blockers are all resolved: `audioop` (PEP 594 removal) → `audioop-lts`; the old `numpy>=1.23,<2` cap → numpy 2; `pyworld` (no cp314 wheel) → lazy import + default f0 extractor `rmvpe` ([ADR-0030](docs/adr/0030-pyworld-lazy-default-rmvpe.md), with an opt-in faster-but-coarser **FCPE** extractor generated offline to a waveform-input ONNX via `poe export-fcpe-onnx` from a `torchfcpe` overlay — not a runtime dep, like HuBERT — [ADR-0049](docs/adr/0049-fcpe-baked-waveform-onnx-f0-extractor.md)); `PyAudio` (no cp314 wheel) → sounddevice ([ADR-0031](docs/adr/0031-audio-pyaudio-to-sounddevice.md)). Don't lower the floor; 3.13 was deliberately skipped (zero runtime gain here — incremental GC was reverted before 3.13.0 final, free-threading is experimental until 3.14 and moot for this GPU/buffer-bound workload — and it is dominated by 3.14).
- `vstreamer-protos` (the gRPC/protobuf contract) is an external wheel dependency, not vendored here — changes to the wire format happen in that repo.
- Tests live in `tests/`, run under `pytest` with `asyncio_mode = "auto"` (no `@pytest.mark.asyncio` needed). The most load-bearing tests are `test_shared_context_routing.py` (routing/`EventAddress`/`Command` conversion) — keep them green when touching `command.py` or `shared_context.py`.
- **`tests/` mirrors the package tree** ([ADR-0088](docs/adr/0088-mirror-test-layout-on-package-tree.md)): `vspeech/lib/audio.py` → `tests/lib/test_audio*.py`, `vspeech/worker/` → `tests/worker/`, `vspeech/stream_vc/` → `tests/stream_vc/`, `vspeech/config.py` → `tests/config/` (one file per section), `cli/` → `tests/cli/`, `scripts/` → `tests/scripts/`, and `vspeech/<mod>.py` → `tests/test_<mod>*.py`. **File names lead with the source module** (`test_audio_rate.py` / `test_audio_resolver.py` / `test_audio_stream_close.py`), so `ls tests/lib/` is both a table of contents and a duplicate check — put a new test where its target module maps, and anything already there is the file to extend instead. The only files directly under `tests/` that are not per-module are the cross-cutting gates (`test_runtime_footprint.py`), which say so in their docstring. Each test directory carries an empty `__init__.py`: the mirror makes basenames collide (`tests/worker/test_playback.py` vs `tests/stream_vc/test_playback.py`) and pytest's default import mode needs the package to tell them apart. This layout replaced a flat 92-file directory in which three duplicate tests had already been written because the existing one could not be found by name.
- **Shared fixtures go in `tests/conftest.py`**, pure builders in `tests/pcm.py` (a fixture cannot serve a module-level helper). `telemetry` is a process-wide singleton and is reset by an **autouse** fixture — never hand-write `telemetry.reset()` in a test again; take `enabled_telemetry` if you need it recording. `stub_device_table` / `record_opened_streams` install the sounddevice fakes and take the caller's own device table and stream class, because those genuinely differ per boundary.
- **The suite runs in parallel by default** (`-n auto` in `addopts`, pytest-xdist — [ADR-0090](docs/adr/0090-test-runtime-collection-and-parallelism.md)): warm, that is 37s → 20s, and the run-to-run spread drops from 43% to 7%, which matters more. **Pass `-n0` to go back to in-process serial** whenever you need `pdb`, `-s`, or readable interleaved output. Two things follow from how the time is actually spent. **A test module must not import at module scope anything the module under test does not already import** — collection imports every file, so one stray heavy import is paid by every run, including one that selects a single test elsewhere (`scipy` in `test_pitch_extract.py` alone cost 6s; it is a test-only dependency `vspeech/` never imports). And **do not defer the heavy imports in `vspeech/` itself** to make tests faster: `sounddevice` / `google.*` / `onnxruntime` at module scope are what the weight gate measures ([ADR-0085](docs/adr/0085-gate-runtime-weight-on-outcome.md)/[0087](docs/adr/0087-weight-guarded-by-measurement-not-named-bans.md)), and moving them into function bodies is the exact shape ADR-0087 warns about. Note that wall-clock here swings 5x with file-cache state (`python -c pass` is 0.16s warm, 1.02s cold), so measure with pytest's own reported seconds, min of 3, and A/B interleaved.
- **GPU/asset requirements are declared as `requires_*` markers**, registered in `pyproject.toml` and evaluated in one `pytest_runtest_setup` hook ([ADR-0089](docs/adr/0089-runtime-asset-gates-as-registered-markers.md)) — not as a hand-written `skipif` per file. `uv run pytest --markers` is therefore the live index of what each skipped test needs (seven env vars' worth), and `uv run pytest -m requires_cuda` runs the GPU set on a machine that has one. Adding a gate means adding the marker to `pyproject.toml` **and** its check to `REQUIREMENTS` in `tests/conftest.py`; a marker registered in only one of the two either never fires or never shows up.
